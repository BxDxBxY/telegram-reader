# Протокол безопасности: как не поймать бан

Telegram блокирует аккаунты не за сам факт чтения через Telethon или Pyrogram.
Триггеры — поведение, похожее на спам-бота: шквал запросов, параллельные потоки,
резкая массовая активность, постоянные новые авторизации. Ниже — что именно делает
tgaudit, чтобы этого не происходило, и что должны делать вы.

## 1. Имитация официального клиента

По умолчанию Telethon отправляет пустые или стандартные параметры устройства —
это заметный признак самописного скрипта. tgaudit всегда передаёт правдоподобные
заголовки (`tgaudit/safety.py:client_kwargs`):

```python
client = TelegramClient(
    'sessions/main',
    api_id=API_ID,
    api_hash=API_HASH,
    device_model="Desktop PC",
    system_version="Linux 6.x",
    app_version="5.0.1",
    lang_code="ru",
    system_lang_code="ru",
)
```

Значения настраиваются в `.env` (`TG_DEVICE_MODEL`, `TG_SYSTEM_VERSION`,
`TG_APP_VERSION`). Разумно указать то, чем вы реально пользуетесь.

## 2. Бережный сбор сообщений (rate limiting)

- **Никакой конкурентности.** Обход чатов строго последовательный, один
  `get_messages` за раз. Тест `tests/test_stage2.py` это фиксирует.
- **Случайная пауза между чатами:** `random.uniform(1.5, 3.5)` секунды.
  Равномерные паузы «ровно 2.0 с» выглядят машинно — поэтому разброс.
- **Длинные передышки:** каждые 25 чатов пауза 15–40 с, как будто человек отвлёкся.
- **Бюджет прогона:** не больше 150 чатов за запуск (`TGAUDIT_MAX_CHATS_PER_RUN`).
  Дальше — завтра; очередь помнит, на чём остановились.
- **Маленькие срезы:** 25 сообщений на чат. Больше 30 не нужно для оценки тематики,
  а нагрузка на API растёт.

Оценка длительности печатается до старта:

```
К выгрузке: 120 чатов × 25 сообщений, ≈9 мин с безопасными паузами.
```

## 3. Обработка FloodWaitError

Telegram при превышении порога возвращает исключение с числом секунд ожидания.
Единственно правильная реакция — поспать ровно столько, сколько просят, и не
долбиться в API заново:

```python
from telethon.errors import FloodWaitError

try:
    messages = await client.get_messages(chat, limit=25)
except FloodWaitError as e:
    print(f"Ждём {e.seconds} секунд...")
    await asyncio.sleep(e.seconds + 2)
```

В tgaudit это `safety.with_flood_retry`. Сверх того:

- если ждать просят дольше `TGAUDIT_FLOOD_WAIT_LIMIT` (по умолчанию 600 с) —
  прогон останавливается с понятным сообщением, а не висит часами;
- больше 5 FloodWait за прогон — тоже стоп: Telegram явно просит сбавить темп;
- всё уже собранное остаётся в БД, повторный запуск продолжит с места остановки.

## 4. Сессия и авторизация

- Создайте `.session` **один раз**: `python -m tgaudit login`.
- Не логиньтесь по SMS-коду при каждом запуске. Несколько авторизаций с одного IP
  за короткое время — почти гарантированная временная заморозка.
- Файл сессии — это полноценный доступ к аккаунту. Он в `.gitignore`; не кладите
  его в облако и не передавайте никому.
- Если сессия «слетела», сначала разберитесь почему, а не логиньтесь повторно подряд.

## 5. Сеть

- Запускайте с той же сети, откуда обычно заходите в Telegram (домашний интернет —
  лучший вариант).
- Публичные дешёвые VPN и «грязные» прокси — плохая идея: IP-адреса таких сервисов
  давно в чёрных списках, а резкая смена гео у аккаунта вызывает подозрение.

## 6. Только чтение

tgaudit не умеет выходить из каналов, удалять чаты и отправлять сообщения — это
осознанное ограничение. Если скрипт выйдет из 100 каналов за две минуты, Telegram
решит, что аккаунт угнан, и выдаст мут или бан.

Отписывайтесь руками по `out/unsubscribe_plan.md`: он сразу разбит на дни
по 20–30 чатов. Между отписками — паузы в несколько минут.

## Чек-лист перед запуском этапа 2

- [ ] `.session` создан заранее, повторных логинов не будет;
- [ ] паузы не меньше 1.5 с (`TGAUDIT_MIN_DELAY`);
- [ ] бюджет на прогон разумный (100–150 чатов);
- [ ] запуск с обычной домашней сети;
- [ ] вы готовы, что прогон займёт минуты, а не секунды.

Если очень хочется ускориться — не надо. Один аккуратный прогон за 15 минут лучше,
чем неделя без доступа к аккаунту.
